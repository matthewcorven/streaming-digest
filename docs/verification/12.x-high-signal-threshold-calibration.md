# Verification: 12.x — High-signal threshold calibration against the real embedding provider

> Append-only evidence. Each run adds a dated entry; prior entries are never overwritten.

---

## Run 1 — 2026-07-27

### Outcome

Calibrating ADR-0012 against the **real Ollama embedding provider** produced a clean own-vs-best-other separation on a curated calibration set, so the default high-signal threshold is now **70%** instead of **80%**.

This run used the production `OllamaEmbeddingService` (the Task 11.3 provider path), not the synthetic prototype embedder. A throwaway spike mode embedded **14 recent-search queries** and **12 candidate cluster fingerprints** with **Ollama `bge-m3`**, then measured each query's cosine similarity to its intended match versus the strongest near-miss non-match. Unlike the synthetic result from 11.3b, the real provider produced a stable absolute gap:

- **own min / median / max:** `0.7143` / `0.7294` / `0.7992`
- **best-other min / median / max:** `0.3847` / `0.4706` / `0.5612`
- **observed gap width:** `0.1530` (`0.7143 - 0.5612`)

Machine-readable evidence: `12.x-high-signal-threshold-calibration.json` (same directory, `Task: 12.x-high-signal-threshold-calibration`).

### Decision

Set `search.highSignalThresholdPercent` default to **70**.

**Rationale:** 70% is the **lowest whole-percent threshold inside the observed gap**. At `0.70` and `0.71`, the calibration set keeps **14/14 intended matches** while allowing **0/14 best-other near-misses**. The prior default of `0.80` is clearly too high for the real provider on this task's calibration set: it passes **0/14** intended matches.

### Calibration set design

The dataset was intentionally small and hand-curated for this task. It paired:

- a **recent-search-style query** ("what the user searched for"),
- an **intended cluster fingerprint** ("the new digest item that should match"), and
- a realistic pool of **near-miss alternatives** in adjacent technical areas.

Topic pairs were chosen to create meaningful non-matches instead of trivial unrelated negatives:

- Blazor JS interop vs Blazor component state
- ASP.NET Core cookie auth vs JWT bearer auth
- pgvector index choice vs hybrid ranking
- Azure Monitor KQL vs OpenTelemetry tracing
- EF Core query tuning vs PostgreSQL indexing
- Kubernetes autoscaling vs Kubernetes observability

### Key observations

1. **The synthetic failure mode is gone.** In 11.3b, best-other outranked own (`0.5931 > 0.4801`) and no threshold separated them. With the real provider, every intended match beat its best other and the gap remained wide enough to support a whole-percent threshold.
2. **80% was not defensible.** It produced `0/14` intended passes on the real-provider calibration set, so keeping the old default would have silently disabled the feature's high-signal path.
3. **70% and 71% are both valid on this dataset; 70% is the safer default.** It preserves the entire curated intended-match set while still suppressing all near-misses. Raising to 72% immediately drops intended recall to `9/14`.
4. **Current Ollama behavior matters operationally.** This run used `/api/embed`, and the production `OllamaEmbeddingService` was updated to accept the real Ollama `embeddings` response shape in addition to the legacy single-`embedding` payload.
