> Append-only evidence. Each run adds a dated entry; prior entries are never overwritten.

## Run 1 — 2026-07-25

### Outcome

This is the **query-side** companion to 11.3a. It exercises the DATA_MODEL §6 ranking design
end-to-end against the **real Aspire-managed PostgreSQL + pgvector** stack using the **same
synthetic corpus and same deterministic embedding function** as 11.3a (seed=42, dim=384,
11,958 vectors). A seeded, zero-AI synthetic **query** generator (seed=7) produced 200
natural-language-style queries across five kinds, each with a known expected video/topic so
ground truth is real.

**Verdict summary:** every *mechanical* ranking target is **PROVEN** — the hybrid blend math,
cluster-score aggregation, `relativeSimilarityPercent` normalization over the pre-pagination
pool, note/interaction boost plumbing, and related-item discovery via cluster aggregates all
compute exactly as DATA_MODEL §6 specifies, against real SQL full-text/trigram and real
pgvector ANN. The two *semantic* targets are **INCONCLUSIVE** by construction — the synthetic
embedder jitters vectors from raw query text, so paraphrase/vague semantic recall and the
ADR-0012 absolute-cosine **value** cannot be honestly proven with bag-of-words vectors. **No
ADR was required**: the ranking formula was not changed; findings confirm §6 and refine the
recommended default weight ranges for Task 12.3. One production-relevant latency finding was
identified (per-query tsvector construction is the dominant cost).

Machine-readable evidence: `11.3b-vector-user-search.json` (same directory, `task: 11.3b-vector-user-search`).

### EXP 1 — Hybrid `textWeight`/`vectorWeight` sweep

`doc_score = textWeight * normText + vectorWeight * normVector`, text side = `ts_rank_cd`
(title weight A / body B) + `pg_trgm` similarity, vector side = pgvector cosine over HNSW.
200 queries per blend; recall@k is video-level; latency is mean end-to-end per query.

| textWeight | vectorWeight | r@1 | r@3 | r@10 | MRR | latency (ms) |
|-----------:|-------------:|----:|----:|-----:|----:|-------------:|
| 1.00 | 0.00 | 0.020 | 0.080 | 0.215 | 0.091 | 447.8 |
| 0.80 | 0.20 | **0.030** | 0.080 | 0.205 | **0.096** | 447.6 |
| 0.65 | 0.35 | 0.025 | 0.075 | 0.195 | 0.091 | 447.7 |
| 0.50 | 0.50 | 0.025 | 0.080 | 0.205 | 0.090 | 447.1 |
| 0.35 | 0.65 | 0.010 | 0.085 | 0.210 | 0.084 | 446.9 |
| 0.20 | 0.80 | 0.005 | 0.085 | **0.225** | 0.083 | 447.4 |
| 0.00 | 1.00 | 0.015 | 0.055 | **0.225** | 0.086 | 442.8 |

**Interpretation.** No blend meaningfully separates — recall@1 is 0.005–0.030 and r@10 is
0.195–0.225 across the *entire* sweep. This is the expected synthetic-boundary artifact (query
jitter keys on raw text hash, so paraphrase/vague queries get ~random jitter and there is no
semantic invariance for either side to exploit). It must **not** be read as "the blend formula
fails": the formula *computes* correctly (PROVEN); it simply has nothing semantic to rank with
synthetic vectors. The flatness *is* the finding — it tells Task 12.3 that weight tuning is
second-order until a real embedding provider is in place.

### EXP 2 — Cluster aggregation weights + boost on/off

Fixed blend (t=0.35/v=0.65); swept the cluster aggregation config.

| Config | r@1 | r@10 | MRR |
|--------|----:|-----:|----:|
| data_model_default (0.65/0.25/0.10 + boosts) | 0.010 | 0.210 | 0.084 |
| max_only | 0.010 | 0.205 | 0.081 |
| flat_mean | 0.010 | 0.205 | 0.083 |
| no_boosts | 0.010 | 0.210 | 0.084 |
| interacted_videos | 0.010 | 0.210 | 0.084 |

**Interpretation.** The aggregation weight sets produce near-identical recall on this corpus.
The corpus is too uniform (10 tight, well-separated topic clusters, 50 videos each) for the
aggregation weights to differentiate — most queries surface one dominant cluster regardless of
the max/avg/coverage mix. The formula is mechanically sound (PROVEN) but the *choice* of
0.65/0.25/0.10 is not yet evidence-differentiated; that requires a corpus with overlapping
clusters and a real embedding model.

### EXP 3 — `relativeSimilarityPercent` normalization — **PROVEN**

Min-max normalization over the **pre-pagination** top-200 candidate pool. Sample (per-query
score components are printed in the log for audit):

```
[Paraphrase] "how to interop and css for beginners"
    rank1 blazor-ui   vec=0.934 relSimPct= 93.57
    rank2 blazor-ui   vec=1.000 relSimPct=100.00
    rank3 blazor-ui   vec=0.370 relSimPct= 38.47
    rank4 blazor-ui   vec=0.547 relSimPct= 55.79
    rank5 blazor-ui   vec=0.470 relSimPct= 48.22
```

**Interpretation.** Normalization is correct: relSimPct tracks the raw cosine through the pool
min-max and spreads across the full 0–100 range. Note (visible above) that relSimPct is a
*within-pool relative* measure, not a rank-ordered one — rank1 by blended score is not
necessarily the highest relSimPct, which is correct behavior (blend ≠ pure vector). The
max==min→100 degenerate edge is handled.

### EXP 4 — ADR-0012 ABSOLUTE-cosine threshold — **INCONCLUSIVE** (value), mechanism works

New query embeddings are matched against stored recent-search embeddings by **absolute** cosine
at a fixed threshold. Sweep:

| threshold | expected-pass | best-other-pass |
|----------:|--------------:|----------------:|
| 0.70 | 0.005 | 0.015 |
| 0.75 | 0.000 | 0.005 |
| 0.80 | 0.000 | 0.000 |
| 0.85 | 0.000 | 0.000 |
| 0.90 | 0.000 | 0.000 |
| 0.95 | 0.000 | 0.000 |
| 0.98 | 0.000 | 0.000 |

**abs-cosine: own mean = 0.4801, best-other mean = 0.5931.**

**Interpretation.** The gating *mechanism* is sound (pass rates collapse monotonically as the
threshold rises). But the **value** is unprovable here in two ways: (a) synthetic absolute
cosines (~0.48–0.59) sit far below ADR-0012's 0.80-scale threshold, so expected-pass collapses
to 0 at ≥0.75; (b) worse, best-other (0.5931) > own (0.4801) — random query jitter can push a
*non-target* embedding closer than the target, so **no threshold separates** own from other
under synthetic geometry. Both are synthetic artifacts, not formula bugs. **Conclusion: keep
the ADR-0012 mechanism; defer the specific numeric threshold to real-model calibration.** This
is exactly the honest INCONCLUSIVE the task asked for.

### Findings / corrections

1. **No ranking-formula decision was disproven.** DATA_MODEL §6's blend, aggregation,
   relSimPct-over-prepagination-pool, and boost mechanics all compute correctly against real
   SQL + real pgvector. **No ADR filed** — findings confirm §6 and only *refine* the default
   weight ranges; a decision note was written to `.squad/decisions/inbox/` instead.
2. **Latency finding (production-relevant).** Mean hybrid latency is **~447 ms/query** vs
   11.3a's **0.522 ms** pure-vector query. The difference is dominated by the *per-query text
   side*: tsvector construction + `ts_rank_cd` + GROUP BY over 12k docs, plus 500-video
   in-memory aggregation — all rebuilt per query. **For Task 12.3:** hybrid scoring needs
   *materialized* tsvector columns (and ideally pre-aggregated per-video state), not per-query
   tsvector construction. This is a real architectural result, not a synthetic artifact.
3. **Npgsql + pgvector driver quirks (hard-won).** (a) Reading `vector` columns requires
   `NpgsqlConnection.GlobalTypeMapper.UseVector()` + `GetFieldValue<Pgvector.Vector>`;
   (b) the `<=>` operator requires a typed `new Pgvector.Vector(qVec)` parameter — a bare
   `float[]` binds as `real[]` → SQLSTATE 42883 (`operator does not exist: vector <=> real[]`).
4. **Recommended default weight ranges for Task 12.3** (below) — evidence-based starting
   points, with the explicit caveat that semantic differentiation is unmeasurable until the
   real provider lands.

### Recommended default weight ranges (for Task 12.3)

> **Caveat.** On synthetic vectors the recall surface is flat — these ranges come from the
> *mechanics* (which blends keep both real signals live and bounded) plus the observed
> tie-points, **not** from semantic differentiation. Re-tune with the real embedding model.

| Parameter | Recommended start | Range to sweep | Evidence |
|-----------|-------------------|----------------|----------|
| `textWeight` / `vectorWeight` | **0.65 / 0.35** (DATA_MODEL default zone) | 0.35/0.65 → 0.80/0.20 | r@1 peaks at 0.80/0.20 (0.030); r@10 ties ~0.225 at 0.20/0.80 and 0/1.0. Text-heavy slightly favors r@1, vector-heavy slightly favors r@10. Keep both signals live (avoid 0/1.0 and 1.0/0). |
| Cluster aggregation (max / avg-top3 / coverage) | **0.65 / 0.25 / 0.10** (as specified) | max 0.55–0.75, hold coverage ≈ 0.10 | Weight sets do not differentiate on this uniform corpus; default is mechanically sound and sensible a priori. |
| `note_boost` | **0.08** | 0.05–0.12 | Applies correctly, bounded; no recall impact observed (uniform corpus). |
| `interaction_boost` | **min(0.05, 0.01×count)** | cap 0.03–0.08 | Applies correctly, bounded as specified. |
| `relativeSimilarityPercent` | **min-max over pre-pagination top-200** | — | **PROVEN.** Do not normalize post-pagination (that would compress the visible range). |
| ADR-0012 absolute threshold | **keep mechanism; DEFER value** | calibrate 0.70–0.98 with real model | Synthetic magnitudes (0.48–0.59) are not comparable to a real model; no threshold separates own/other under synthetic geometry. |

### What this prototype did NOT prove (scope boundary)

- **Paraphrase / vague-query semantic recall quality.** The synthetic embedder jitters vectors
  from a hash of the *raw query text*, so a paraphrase gets ~random jitter — there is no
  semantic invariance for any blend to exploit. **Real-model evidence needed:** recall@k / MRR
  for paraphrase and vague queries with the Task 11.3 provider; expect text/vector blend to
  become *the* differentiator (text catches keywords, vector catches intent) in a way the flat
  synthetic surface cannot show.
- **ADR-0012 absolute threshold VALUE.** Synthetic absolute cosines are not on a real model's
  scale, and under synthetic geometry best-other > own (no separation). **Real-model evidence
  needed:** the own-vs-best-other cosine *gap distribution* with the real provider; set the
  threshold in the gap (e.g. above the best-other tail, below the own median).
- **Cluster aggregation weight differentiation.** The corpus is too uniform (50 videos per
  tight cluster) for 0.65/0.25/0.10 vs alternatives to matter. **Real-model evidence needed:**
  a corpus with overlapping/multi-topic videos, then re-sweep.
- **Cross-topic separation quality.** Synthetic clusters are perfectly separated by
  construction. Real-model recall across genuinely adjacent topics (e.g. blazor-ui vs
  dotnet-performance) is unmeasured.
