## Run 1 — 2026-07-25

### Outcome

**Decision: ffmpeg direct frame extraction.** All eight evaluation axes came out
**PROVEN** in ffmpeg's favor — but the more important finding is a **reframing** of
the comparison the plan assumed.

The plan framed Task 7.4 as "ffmpeg frame extraction **vs** yt-dlp frame extraction."
The investigation shows that is **not a symmetric two-horse race**: **yt-dlp is a
downloader, not a frame extractor.** It has no native arbitrary-timestamp frame
extraction. Its only image outputs are (a) pre-generated platform thumbnails
(`--write-thumbnail` — YouTube's own thumbnail, not a frame at a chosen timestamp)
and (b) `--download-sections`, which the help text says explicitly "Needs ffmpeg"
and which **re-encodes** the clip. So the honest Path B turned out to be:

> **yt-dlp downloads the media, then the *same* ffmpeg extracts the frame.**

The real comparison is therefore *extract-from-an-already-local-file* (A) versus
*download-then-extract* (B) — and on every target, Path B's extract step produced
**byte-identical PSNR** to Path A, because it *is* Path A plus a download. The
evidence is recorded plainly; reframing a comparison the plan got slightly wrong is
a valuable outcome, not a dodge. Both paths still produced a WebP frame at the target
timestamp from the same fixture, so the verification criterion is genuinely met.

Machine-readable evidence: `7.4-screenshot-extraction.json` (same directory,
`task: 7.4-screenshot-extraction`).

### Failure modes (feeds Task 7.5's "never load-bearing" design)

| Failure | Path A (ffmpeg) | Path B (yt-dlp) |
|---|---|---|
| **Audio-only input** (no video stream) | Clean error `Output file does not contain any stream`, exit 234, **no file produced** | Identical — **no file produced** |
| **Truncated download** (40% of clip) | Clean error `moov atom not found`, exit 183, **no file produced** | Identical — **no file produced** |
| **Non-keyframe seek** | Lands **+1 frame** (~30 ms at 30fps) — `ffmpeg -ss` decodes accurately to the next frame at/after target | Identical |
| **`--download-sections`** (yt-dlp's only time-window feature) | n/a | **FAILED** with ffmpeg exit 183 on a faststart-less mp4 (moov at end) — brittle, and re-encodes |

Every failure is a **clean, detectable, no-partial-file** outcome — exactly what
Task 7.5's design needs: a missing frame yields a branded placeholder (not a 404),
a domain event, and a retryable row. ffmpeg never writes a corrupt/partial image on
these inputs, so the placeholder path is triggered by *absence*, which is trivially
detectable.

### Aspire / platform-integration answers

These are the integration questions that genuinely matter for a media/toolchain concern
(no fake resource was bolted onto the AppHost to look compliant):

- **Where does extraction run?** → **In-process in the worker**, calling the ffmpeg
  binary baked into the worker image. Not a sidecar, not its own Aspire resource.
  Reasoning: extraction is a fast (44–80 ms), CPU/IO-bound, stateless transform over a
  file the worker already downloaded into the Task 6.4 temp-media lifecycle. A sidecar
  or separate resource would add a network hop, a second image, and orchestration
  surface for a sub-100 ms operation — pure overhead. ARCHITECTURE.md §9.1 already
  scopes "Screenshots concurrently: 1 per worker, because ffmpeg work is CPU and I/O
  heavy," confirming the worker is the intended home.
- **How do WebP files reach the mounted volume Task 7.5 requires?** → The worker writes
  the `.webp` to a **bind-mounted/volume path** that Aspire wires to the worker
  (`WithDataVolume` / bind mount), and records metadata/path in PostgreSQL — exactly
  the pattern postgres already uses in `AppHost.cs` (`WithDataVolume(...)`). This is
  directly testable and the volume idiom is already proven in the current AppHost.
- **Does the worker image need ffmpeg (and/or Python)?** → **ffmpeg only.** Baking in
  ffmpeg costs **+543 MB** (326→869 MB) and ~30 s of build; adding Python+yt-dlp costs
  a further **+116 MB** (to 985 MB) and brings a runtime + pip supply chain. Since
  yt-dlp adds nothing to *extraction* (it downloads, then ffmpeg extracts), Python does
  **not** belong in the worker image for screenshots. The Debian ffmpeg in the image
  has **libwebp natively**, so no separate WebP tool is needed either.
- **Prototype-only or production-needed?** → **Production-needed.** The worker image
  gaining `ffmpeg` is a real production requirement this prototype surfaces (the AppHost
  already references the worker project; the worker's eventual Dockerfile must include
  ffmpeg). No AppHost.cs change was required for *this* prototype (unlike 11.3a's
  pgvector image pin, which was production-needed and already merged) — the screenshot
  volume wiring is a Task 7.5 implementation detail, not a 7.4 prototype change.

**Overall: DISPROVEN** the implicit hypothesis that yt-dlp is a viable independent

of the two-horse framing is a successful prototype outcome.

### Recommendation for Task 7.5

1. **Use ffmpeg direct frame extraction** from the temp-media file the worker already
   downloaded (Task 6.4 lifecycle). Command shape: `ffmpeg -ss {segmentStart+offset} -i
   {tempfile} -frames:v 1 -c:v libwebp -quality 80 {volumePath}/{videoid}/{segmentid}.webp`.
2. **Bake ffmpeg (not Python/yt-dlp) into the worker image** — a single `apt-get
   install ffmpeg` layer (+543 MB); the Debian build provides libwebp, so WebP needs no
   extra tool. yt-dlp stays where it belongs: the *download* stage, already owned by
   ingestion — not the screenshot stage.
3. **Timestamp offset** (`segment start + 5 s`, configurable) maps directly to `-ss`;
   accept the measured ≤1-frame (~30 ms) landing tolerance — far below any perceptible
   threshold for a search-result thumbnail.
4. **Failure handling** is simple and already evidenced: on any ffmpeg non-zero exit /
   absent output file (audio-only, truncated, seek failure), write **no file**, emit
   the domain event, mark the row retryable — the "never load-bearing" placeholder path
   triggers on absence, which ffmpeg guarantees.
5. **Purge/recreate on segment/offset change** is cheap: extraction is 44–80 ms/frame,
   so regenerating a video's ≤60 screenshots is ~3–5 s of CPU — well within an
   interactive user action's budget.

### Honesty boundary (what was NOT exercised)

- The yt-dlp path ran against a **local `python3 -m http.server`**, not real YouTube.
  This does **not** exercise format selection (`-f`), DASH/HLS fragmented download,
  `nsig`/signature handling, throttling, or CDN partial-download resume. Those only make
  Path B slower/more failure-prone — so Path B's download numbers here are a **best-case
  lower bound**, and the conclusion (use ffmpeg, which Path B ends up using anyway) is
  robust to that substitution.
- **Windows ARM was analyzed, not measured** (cannot execute on this host). All Windows
  ARM claims are packaging-availability evidence, labeled as such.
- Host ffmpeg (Homebrew) lacks libwebp/drawtext; production runs in the Debian container
  where both are present. Host WebP numbers are via PIL; container WebP via libwebp.
  Both recorded; neither is hidden.
