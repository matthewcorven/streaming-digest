### Numbers (HNSW vs IVFFlat at MVP scale)

| Index | Build (ms) | Avg query (ms) | Recall@10 | Size (KB) |
|-------|-----------:|---------------:|----------:|----------:|
| **HNSW** (default) | 979 | 0.522 | 0.99 | 23,928 |
| **IVFFlat** (lists=100, probes=10) | 422 | 0.509 | 0.98 | 19,640 |
| Exact seq-scan baseline | — | 3.223 | 1.00 | — |

**Interpretation.** At MVP scale (~500 videos / ~12k vectors) both indexes are sub-millisecond
and trivially small. HNSW costs ~2.3× build time and ~1.22× index size for a marginal recall
edge; either is operationally viable. **Recommendation: HNSW as the MVP default** — pgvector
0.8.5 builds it incrementally (no need to pre-populate before indexing, unlike IVFFlat), it
needs no tuning of `lists`/`probes`, and its recall headroom matters once a real embedding
model replaces the synthetic one. This is a *refinement* of DATA_MODEL §3.22 (which left
"HNSW or IVFFlat depending on version/size" open), not a contradiction of it.

> **Boundary (important).** These recall numbers are **internal-consistency checks only.**
> The synthetic embedder produces 10 tight, well-separated topic clusters — data that flatters
> both indexes. The recall/latency figures **do not transfer** to a real embedding model.
> What the synthetic setup *does* prove is storage, indexing mechanics, cardinality, centroid
> math, staleness derivation, and query mechanics. Real semantic recall quality must be
> re-measured with the real provider in Task 11.3.

### Aspire / pgvector AppHost note (production-relevant)

The AppHost's stock `postgres` image has **no pgvector extension**. The prototype required
(and production will require) pinning the image in `src/StreamingDigest.AppHost/AppHost.cs`:

```csharp
builder.AddPostgres("postgres")
    .WithImage("pgvector/pgvector", "pg17")
    .WithImageRegistry("docker.io")
    .WithDataVolume("streamingdigest-postgres-data")
    .AddDatabase("streamingdigest");
```

**This change is needed by production, not just the prototype**, and should be promoted via a
normal PR (the throwaway prototype branch is not merged to main). `CREATE EXTENSION vector;`
then succeeds (verified: pgvector 0.8.5, HNSW index builds).

**Gotcha (data volume).** The named data volume `streamingdigest-postgres-data` persists across
image changes. If the volume was initialized by the stock `postgres:18.x` image, the `pg17`
image fails `initdb` with `directory "/var/lib/postgresql/data" exists but is not empty`. Fix
before the first pgvector run: `docker volume rm streamingdigest-postgres-data` (and remove the
stale container so Aspire recreates it with the new image).

**Aspire CLI vs SDK version.** Aspire CLI 13.2.2 vs the pinned `Aspire.AppHost.Sdk/13.4.6`
did **not** block: `dotnet run` on the AppHost project uses the pinned SDK, and the AppHost
built and ran cleanly. Documented as a non-issue for this environment.

### Findings / corrections

1. **No storage or index decision was disproven.** The DATA_MODEL §5 construction rules,
   ADR-0001 staleness derivation, ADR-0004 shared-embedding cardinality, and §3.23 centroid
   construction all held against real infrastructure.
2. **Staleness derivation is expressible in pure SQL.** Postgres `sha256(convert_to(coalesce(title_effective,'') || E'\n' || coalesce(body_effective,''),'UTF8'))`
   matches the .NET `SHA256` hex of the same canonical string byte-for-byte (0 mismatches).
   This validates the "computed view or function" ergonomic — staleness can be derived
   database-side without trusting a stored flag.
3. **ADR-0004 dedup is small at MVP scale but real.** 12,120 doc rows → 11,958 distinct hashes
   (162 duplicates: 120 intended shared-resource copies + ~42 incidental template collisions),
   a 1.34% embedding-computation saving. At production volume with a real (paid) embedding
   provider this dedup directly reduces provider calls and cost.
4. **Recommendation: default the MVP to HNSW** (see table above). This refines §3.22.
5. **No new ADR filed.** The findings confirm existing decisions and only *refine* the index
   default. Per the task, an ADR is recorded only if findings change a storage/index decision;
   they do not overturn one. The HNSW-default recommendation is captured here and can be folded
   into the §3.22 implementation note.

### What this prototype did NOT prove (scope boundary)

- **Real semantic recall / ranking quality.** Requires the real embedding provider (Task 11.3).
- **HNSW vs IVFFlat at >MVP scale** (~2,000-video dataset). Extrapolation to ~48k vectors is
  plausible but not measured here; re-measure before assuming at that scale.
- **Hybrid (vector + full-text) ranking.** DATA_MODEL §6 hybrid scoring was out of scope; only
  the vector/embedding side was exercised.
- **Concurrent write/read behavior** and index maintenance cost under churn.
